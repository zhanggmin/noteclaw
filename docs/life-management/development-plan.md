# Life 管理功能开发计划

本文档记录目标管理、习惯养成、日常记录一体化功能的分阶段开发计划。开发过程中如范围、阶段或关键技术决策发生变化，应同步更新本文档。

## 开发原则

- **分步骤交付**：该功能横跨本地数据、UI、提醒、Agent 工具和后续洞察，必须按阶段推进，避免一次性做完整导致反馈周期过长。
- **本地核心优先**：先稳定领域模型、序列化、本地仓储和基础 UI，再接入 Agent 工具、提醒、复盘和洞察。
- **记录 + 习惯先行**：MVP 第一轮优先完成日常记录和习惯养成闭环，目标管理后置。
- **目标采用混合关联模型**：目标可以收纳展示习惯、计划和记录，但不物理包含它们；习惯、计划、记录都是独立实体。
- **开发文档同步更新**：每个阶段开始、完成、延期或调整时，都应在 `docs/life-management/` 下补充记录。

## 核心模型边界

开发实现时采用以下语义边界：

- **目标 `Goal`**：回答“我要成为什么/达成什么”，是结果对象。
- **习惯 `Habit`**：回答“我每天/每周重复做什么”，是重复行为对象。
- **计划 `Task/Plan`**：回答“我接下来具体做什么”，是任务/待办对象。
- **记录 `LifeRecord`**：回答“我实际发生了什么”，是事实事件对象。

待办首版采用轻量主题模型：`TodoList` 表示一个待办主题，`TodoItem` 表示该主题下的一条待办，例如“周末要做的 10 件事”对应一个主题和十个待办项。该能力先独立存在，后续再通过 id 关联目标。

关系模型：

```text
Goal
  -> links Habit[]
  -> links Task[]
  -> links LifeRecord[]
  -> owns Milestone[]
```

只有 `Milestone` 适合作为目标的内部阶段节点。`Habit`、`Task/Plan`、`LifeRecord` 应作为独立实体保存，通过 id 与目标建立关联。

## MVP 范围

第一轮 MVP 聚焦“记录 + 习惯先行”。

包含：

- 本地 JSON/JSONL 仓储。
- 内置记录模板：加油、理发、汽车保养。
- 自定义记录模板：用户可以新建模板，定义模板名称和字段。
- 日常记录创建、编辑、归档/删除、搜索、日期筛选。
- 习惯创建、编辑、启停、打卡、跳过、基础统计。
- 轻量待办主题：用户可以创建一个主题并添加多条待办，例如“周末要做的 10 件事”。
- 今日视图的基础入口：今日待办、今日习惯、最近记录、快捷创建。
- 日期型提醒：习惯提醒、记录后续提醒。
- Agent 工具基础能力：创建记录、搜索记录、创建习惯、习惯打卡。

暂不包含：

- 云同步。
- 多人协作。
- OCR 票据识别。
- 完整目标复盘和高级目标仪表盘。
- 复杂项目计划和任务依赖。
- 基于里程阈值的后台自动检测。
- 高级洞察仪表盘。
- 加密数据库迁移。

## 存储决策

MVP 使用 JSON/JSONL 存储是可行的，但这只是首版实现策略，不是永久承诺。

采用 JSON/JSONL 的原因：

- 当前项目已有配置、会话、cron、watcher、action center 等 JSON/JSONL 持久化模式，工程风格一致。
- MVP 先做记录和习惯，数据量不会马上达到必须使用数据库的规模。
- 文件存储便于调试、备份、导出和迁移。
- 通过 repository 隔离存储实现后，后续可以替换为 SQLite/Drift，而不影响 UI、service 和 tool。

迁移到专用本地数据库的触发条件：

- 记录量达到几千到几万条后，搜索、筛选、分页明显变慢。
- 需要复杂查询，例如多标签组合、金额区间、车辆维度、时间聚合、全文搜索。
- 需要事务保障，例如一次操作同时更新记录、习惯、提醒和统计缓存。
- 后续引入同步冲突处理，需要更强的索引、迁移和一致性能力。

实现要求：

- UI、application service、Agent tool 不直接读写 JSON/JSONL 文件。
- 所有读写通过 `LifeManagementRepository` 完成。
- repository 对外暴露领域对象和查询方法，不暴露文件路径和文件格式。
- JSON/JSONL 文件需带 schema version 或具备兼容读取能力。

## 导航决策

Life 管理功能作为高频日常入口，应放入底部 Tab；频道管理属于低频连接配置，应从底部 Tab 移入 Settings。

调整后的底部 Tab：

```text
Chat / Notes / Life / Agents / Settings
```

Settings 中保留 Channels 入口，用于配置 Telegram、Discord、Slack、Signal、WhatsApp 等外部频道。

实现要求：

- Life Tab 初期可以是功能入口页，后续逐步接入习惯、记录、今日视图。
- ChannelsScreen 保持原有能力，只改变入口位置。
- analytics 事件从 `bottom_nav_channels` 调整为 `bottom_nav_life`。
- 网关默认不自启动，用户可在 Settings -> Gateway 中手动开启 auto-start。

## 记录模板与列表决策

记录模块采用“模板优先”的信息架构。记录列表默认展示记录模板，而不是直接平铺每一条记录。

核心规则：

- 系统内置模板只提供首批默认能力，包括加油、理发、汽车保养。
- 用户可以新建自定义记录模板，用于覆盖更多生活记录场景。
- 记录列表页面中，相同模板下的记录合并成一条模板卡片。
- 模板卡片显示模板名称、最近一次记录时间、该模板下记录总次数。
- 点击模板卡片后进入模板记录明细页，查看该模板下的所有记录。
- 记录列表页面的“新建”按钮用于新建记录模板，而不是直接新建某条记录。
- 新建某条记录应放在模板详情页内完成，因为记录必须归属于某个模板。

调整后的记录流程：

```text
记录列表
  -> 模板卡片列表
  -> 点击某个模板
  -> 模板记录明细页
  -> 新建/编辑该模板下的一条记录
```

后续实现需要把当前“记录列表直接展示所有记录”的 UI 调整为模板聚合视图。

## 分阶段路线

### Phase 0: 文档与模型决策

目标：确认开发边界，避免后续实现反复调整基础模型。

交付物：

- 更新架构文档中的混合关联模型。
- 明确 `Goal`、`Habit`、`Task/Plan`、`LifeRecord` 的职责。
- 明确 MVP 采用“记录 + 习惯先行”。
- 明确首版存储采用 JSON/JSONL，后续可迁移 SQLite/Drift。

验收标准：

- 架构文档和开发计划不冲突。
- 文档不再暗示习惯和计划必须属于某个目标。
- “计划”统一定义为任务/待办，不扩展为日历日程或复杂项目计划。

### Phase 1: 领域模型与本地仓储

目标：先建立可测试、可迁移的本地数据核心。

当前状态：已开始实施。

交付物：

- 新增 `lib/features/life_management/` feature 目录。
- 新增领域模型：`Habit`、`HabitCheckIn`、`LifeRecord`、`RecordTemplate`、`ReminderRule`。
- 新增本地仓储：读取、写入、追加、更新、归档、删除。
- 新增序列化和 schema version。
- 初始化内置模板：加油、理发、汽车保养。

建议存储文件：

```text
{app_documents}/flutterclaw/life_management/
  habits.json
  habit_checkins.jsonl
  records.jsonl
  templates.json
  todo_lists.json
  todo_items.jsonl
  attachments/
```

验收标准：

- 可以创建、读取、更新、归档习惯。
- 可以追加、查询习惯打卡事件。
- 可以创建、读取、搜索、归档日常记录。
- 内置模板首次启动时可自动初始化，重复启动不重复写入。

测试要求：

- 模型 JSON 序列化/反序列化测试。
- repository 读写测试。
- schema version 兼容测试。
- 内置模板初始化测试。

### Phase 2: 记录与习惯核心 UI

目标：让用户不依赖 Agent，也能在 App 内完成记录和习惯闭环。

交付物：

- 新增记录时间线页面。
- 新增记录创建/编辑页面。
- 新增记录模板创建/编辑页面。
- 新增模板聚合记录列表页面。
- 新增模板记录明细页面。
- 新增习惯列表页面。
- 新增习惯创建/编辑页面。
- 新增习惯快捷打卡入口。
- 新增基础今日视图入口：今日习惯、最近记录、快捷按钮。

记录 UI 能力：

- 在记录列表页面新建记录模板。
- 同一模板的记录在列表页面合并成一条模板卡片。
- 模板卡片展示最近记录时间和总记录次数。
- 点击模板卡片进入该模板的记录明细页。
- 在模板记录明细页新建该模板下的记录。
- 支持自由文本备注和结构化字段。
- 支持按日期范围、模板、关键词筛选。
- 支持编辑、归档、删除。

习惯 UI 能力：

- 创建每日、每周、指定星期习惯。
- 支持启用/暂停。
- 支持完成、跳过、补记。
- 展示最近打卡状态、连续天数、近 7/30 天完成率。

验收标准：

- 用户能在 App 内完成一条加油、理发或汽车保养记录。
- 用户能新建一个自定义记录模板。
- 记录列表能按模板聚合，而不是平铺所有记录。
- 点击模板卡片后能查看该模板下的全部记录。
- 用户能创建一个习惯并完成当天打卡。
- 退出重进 App 后数据仍存在。
- 空状态、错误状态和加载状态可用。

测试要求：

- 核心 Widget 测试覆盖记录列表、习惯列表、空状态。
- 手动验收记录创建、编辑、删除/归档、筛选。
- 手动验收习惯创建、打卡、跳过、补记。

### Phase 3: 提醒与今日视图增强

目标：让 life 管理从“记账式记录”变成日常可执行系统。

交付物：

- 接入 `NotificationService`，支持日期型提醒。
- 接入或复用 `CronService` 做周期检查。
- 支持习惯提醒时间。
- 支持记录后续提醒，例如理发 30 天后提醒、汽车保养到期日提醒。
- 增强今日视图：今日习惯、今日提醒、逾期提醒。

验收标准：

- 创建习惯时可设置提醒时间。
- 修改或暂停习惯会同步更新提醒。
- 创建记录时可设置后续提醒。
- 删除或归档对象会取消关联提醒。

测试要求：

- reminder rule 序列化测试。
- 提醒创建、更新、取消的服务层测试。
- 手动验收本地通知触发。

### Phase 4: Agent 工具与快速捕获

目标：让用户可以通过自然语言和外部频道操作记录、习惯。

交付物：

- 新增 `life_record_create` 工具。
- 新增 `life_record_search` 工具。
- 新增 `life_habit_create` 工具。
- 新增 `life_habit_checkin` 工具。
- 新增 `life_capture_parse` 初版解析能力。
- 在 `toolRegistryProvider` 中注册 life-management 工具。

工具行为：

- 工具只调用应用服务，不直接读写文件。
- 创建记录、创建习惯、打卡为低风险操作，可以在意图明确时直接执行。
- 删除、批量修改、敏感记录应要求确认，首版可以不暴露删除工具。
- 自然语言解析输出待确认 payload，避免误写高风险数据。

验收标准：

- 用户可通过聊天创建一条加油记录。
- 用户可通过聊天完成一个习惯打卡。
- 用户可搜索最近记录。
- 工具执行失败时返回明确错误信息，不产生半写入数据。

测试要求：

- 工具参数校验测试。
- 工具调用应用服务的集成测试。
- 手动验收聊天创建记录、习惯打卡、搜索记录。

### Phase 4.5: 轻量待办主题

目标：在完整目标管理前，先交付可独立使用的任务/待办能力，覆盖“周末要做的 10 件事”这类主题清单场景。

当前状态：已完成首版实现。

交付物：

- 新增 `TodoList` 模型，表示一个待办主题。
- 新增 `TodoItem` 模型，表示主题下的一条可完成待办。
- 新增 `todo_lists.json` 和 `todo_items.jsonl` 本地持久化。
- 新增待办主题列表页、主题编辑页、主题详情页。
- 支持新增、编辑、完成、恢复、归档待办项。
- 支持待办项可选截止日期。
- Life 首页新增“今日待办”，展示今天到期和已逾期的未完成待办。
- Life 首页快捷创建新增“新建待办”。

实现原则：

- `TodoList` 和 `TodoItem` 独立存在，不强制属于目标。
- 首版不支持任务依赖、优先级、重复任务、看板或复杂项目计划。
- 归档待办主题后，该主题下未完成待办不再出现在“今日待办”。
- 待办截止日期只用于展示今日/逾期，不在首版触发本地通知。

验收标准：

- 用户能创建“周末要做的 10 件事”主题。
- 用户能在主题下添加 10 条待办。
- 用户能勾选完成或恢复一条待办。
- 用户能给待办设置截止日期。
- 今日/逾期待办会显示在 Life 首页。
- 退出重进 App 后主题和待办状态仍保留。

测试要求：

- `TodoList`、`TodoItem` 序列化和仓储读写测试。
- 待办完成、归档、按主题查询测试。
- 今日/逾期待办过滤测试。
- Life 首页和待办列表 Widget 测试。

### Phase 5: 目标与计划接入

目标：在记录和习惯稳定后接入目标管理，并保持混合关联模型。

前置轻量待办已作为计划能力的第一步落地：先支持独立待办主题和待办项，不包含复杂项目依赖、看板或目标强绑定。Phase 5 需要在此基础上补齐目标、里程碑和目标关联关系，而不是重做待办数据模型。

交付物：

- 新增 `Goal`、`Milestone`、`Task/Plan` 模型。
- 新增目标仓储和服务。
- 新增目标列表和目标详情页面。
- 支持目标关联已有习惯、待办主题/待办项和记录。
- 支持目标的手动进度、任务进度、关联数据进度。
- 新增基础目标工具：`life_goal_create`、`life_goal_update`、`life_goal_list`。

实现原则：

- 目标可以收纳展示习惯和计划，但不物理包含它们。
- 习惯可以不关联任何目标。
- 一个习惯可以关联多个目标。
- 计划可以独立存在，也可以关联一个或多个目标。
- 目标归档不应删除关联习惯、计划或记录。

验收标准：

- 用户能创建目标并添加里程碑。
- 用户能将已有习惯关联到目标。
- 用户能将任务/计划关联到目标。
- 目标详情能展示关联习惯、计划和记录。
- 目标归档后，关联对象仍保留。

测试要求：

- 目标、里程碑、任务序列化测试。
- 目标关联关系测试。
- 目标归档不级联删除测试。
- 手动验收目标详情聚合展示。

### Phase 6: 复盘、洞察、导入导出

目标：补齐长期使用价值和数据可迁移能力。

交付物：

- 周/月复盘生成。
- 习惯完成趋势。
- 记录类别统计。
- 用车相关统计：加油金额、保养费用、里程趋势。
- 完整 JSON 导出。
- 日常记录 CSV 导出。
- 周/月复盘 Markdown 导出。
- 隐私设置和日志脱敏强化。

验收标准：

- 用户可查看最近一周习惯完成情况。
- 用户可查看记录分类统计。
- 用户可导出完整备份。
- 导出的 JSON 可被重新导入或作为迁移基础。

测试要求：

- 洞察计算测试。
- 导出格式测试。
- 导入兼容测试。
- 敏感字段日志脱敏检查。

## 跨阶段工程要求

- 每个阶段完成后运行 `flutter analyze`。
- 涉及模型、仓储、序列化、统计逻辑时运行 `flutter test`。
- 涉及 UI 时补充 Widget 测试或手动验收清单。
- 任何影响范围、数据模型、工具接口的决策都要更新 `docs/life-management/` 下文档。
- 不在 `lib/core/app_providers.dart` 中堆积过多 feature 细节；优先在 feature 内维护 provider，再通过核心 wiring 注册必要入口。
- 工具层不直接写文件，统一调用 application service。
- 洞察和统计优先从事件推导，缓存只能作为优化，不作为唯一事实来源。

## 风险与处理

| 风险 | 处理方式 |
|------|----------|
| 一次性范围过大 | MVP 只做记录 + 习惯，目标后置 |
| JSON/JSONL 查询能力不足 | repository 隔离存储实现，后续可迁移 SQLite/Drift |
| Agent 误写数据 | 高风险操作要求确认，首版不暴露删除工具 |
| 提醒状态与数据状态不一致 | 提醒由 life-management 服务统一管理，编辑/归档时同步更新 |
| 目标和习惯关系复杂 | 使用关联模型，避免目标级联拥有习惯 |
| 敏感记录泄漏 | 默认本地存储，日志脱敏，LLM 分析需用户明确触发 |
